# Evidence assessment

The standalone runner assesses saved selection receipts and exact source contexts
relative to research needs. The application can invoke the V2 component profile in opt-in research mode.
It does not verify whole claims or assess source reliability.

Configuration: `config/judges.yaml`. Prompt:
`experiments.evidence_judgment_v1` in `config/prompts.yaml`. Model selection uses
`MODEL_JUDGE`, then the catalog default. Defaults: three concurrent calls, three
total calls, low effort, and no automatic retries.

`need_components_v2` is an optional experimental profile for one need per job.
It records component descriptions, evidence-relative statuses, explanations and
directional references. Source IDs, URLs and absolute code-point offsets are
resolved from validated source snapshots, not generated by the model. No evidence
produces an insufficient component without a model call. Exact quote validation
does not establish semantic support, complete decomposition or source reliability.
The standalone runner retains its existing default; the opt-in application flow selects this profile.
For a standalone run, pass `--method need_components_v2` to the evaluation runner.

Human-readable vocabulary is centralized in `config/judgment_labels.yaml`.
It separates evidence relations, coverage, need results and execution states.
Loading a judge validates this catalog against typed Python label sets: unknown,
missing or renamed keys fail before inference. Titles and descriptions are editable;
changing executable labels also requires a schema and consumer update. Status
derivation and validation rules remain in code. The catalog is not automatically
inserted into model prompts or exposed in the application UI.

Legacy contracts use `insufficient` for both irrelevant and relevant but
inconclusive evidence. The selectable `need_evidence_relevance_v1` candidate uses
the versioned `relevance_v1` contract to separate `relevant`, `irrelevant` and
`uncertain` relevance from directional relations. Its per-passage `basis` is
`direct`, `inference` or `none`. A passage about the correct entity may be relevant
but lack the requested attribute. Irrelevant/uncertain evidence cannot establish
a directional relation or material coverage. Directional evidence requires a
direct or inferred basis and exact quotations.

The candidate records `scope_note` and `conflict_type` at need level. Opposing
relations require `same_component`, `different_components` or `unclear`; otherwise
the conflict type is `none`. This does not establish source independence or trust.
The original status rules remain evidence-relative. The default is still V1.2;
the candidate is not connected to the application graph or UI. Provider and
validation errors remain execution states, never evidence relations or factual
conclusions. No confidence percentage is defined.

The `need_evidence_v1_1` profile reconciles evidence with
`coverage_summary` and records `time_basis` separately. The original
`need_evidence_v1` profile and response contract remain available for replay.

The selected `need_evidence_v1_2` profile preserves those semantic rules with a
compact transport contract. Request-local evidence aliases (`E1`, `E2`, etc.)
replace long persistent IDs in the model input and output. The request schema
enumerates allowed aliases separately for each need and fixes the number of
evidence assessments. Code still rejects omitted, duplicated, foreign or modified
aliases, then restores canonical IDs before citation validation and persistence.
It never repairs a malformed ID by guessing. Results include the alias map for
short references used in explanation text; aliases have meaning only within that
packet. Source text, URLs and publication context remain available to the model;
internal receipt IDs and source offsets stay in the canonical packet.

V1.2 allows at most two exact excerpts per evidence item, 400 characters each,
and 240-character explanations. Its profile-specific completion limit is 8192;
older profiles keep the 4096 limit. This provides headroom, not a guarantee that
every packet fits. A `length` finish reason produces `model_output_truncated`,
preserving usage and finish reason without parsing partial JSON, caching it as a
success, or retrying automatically. Three previously invalid saved-source cases
completed in one bounded v1.2 trial. This is not a general reliability estimate.

## Contract

1. Rebuild inputs from explicit selection receipts; validate case, need, page,
   passage and context associations before any model request.
2. Send the needs and their evidence together. The model assesses every assigned
   evidence ID as `supports`, `contradicts`, or `insufficient`, with `complete`,
   `partial`, or `none` coverage and literal excerpts.
3. Code rejects foreign/missing IDs and excerpts that are not literal, unique
   substrings of their supplied context. Absolute source offsets are resolved by
   code, not generated by the model.
4. Derive need statuses deterministically and persist the packet, result,
   citations, usage and selection links in the separate research workspace.

Directional evidence on both sides produces `mixed`, including different
components of one need; this does not imply independent sources disagree.
For v1.1, complete collective coverage with resolved time and no remaining gaps
can produce `supported` or `contradicted`, depending on the evidence relation.
Several partial excerpts may collectively answer a need; individual shortcomings
must not be copied into need-level gaps when another excerpt resolves them.
Remaining cases are `insufficient`. The legacy v1 contract still requires an
individually complete directional assessment. Partial coverage that remains
incomplete collectively cannot establish support for an entire need.
These are evidence-relative labels; validation does not prove semantic accuracy.

No selected evidence produces an insufficient result without a model call. Schema,
citation, transport and provider failures remain errors, never fabricated verdicts.
Queued calls stop on failure; already active calls may finish. Valid responses can
be replayed from the workspace cache. Publication dates are reported metadata;
fetch time is not publication time. Repeated excerpts are not independent sources.

## Run

```powershell
python -m evals.judge_evidence --workspace .local/retrieval/example.sqlite `
  --jobs .local/judge-jobs.json --output docs/local/experiments/new-judge-run
```

Each job contains `case_id`, `need_ids`, and `selection_ids`. Without
`--allow-live-judging`, the runner only uses cached responses or no-evidence results.
Live calls also require existing Meta opt-in settings. Use a new output directory
for every run. Local artifacts include requests, raw responses, quota headers,
inputs, results, usage and receipts, without request credentials.

Unknown dates, missing reference points, truncated context and unassessed source
reliability remain limitations. A single source may contradict an alleged value
without proving global real-world falsity. Numeric confidence, full-claim rollups,
source-trust scoring and automatic follow-up searches are not implemented here.

## Temporal provenance

Raw reported publication dates remain in the evidence packet. Code additionally
normalizes explicit ISO/RFC dates and reports `missing`, `unambiguous`,
`conflicting`, or `unparseable` metadata. Ambiguous numeric dates and missing years
are not guessed; fetch time never fills publication time. Normalization does not
verify the metadata or the fact's effective period.

The model must state whether temporal grounding comes from explicit source text,
publication context, is unnecessary, or is unresolved. Publication context must
reference evidence in the same need with unambiguous normalized dates. A
contemporaneous descriptive statement may be treated as what the source reported
at publication, with that assumption disclosed. A retrospective, forecast or
different effective period cannot inherit publication time automatically.

Coverage and temporal references are structurally validated; their semantic
adequacy still requires review. An unresolved temporal basis cannot be paired with
complete collective coverage. These changes do not add source-trust scores.
